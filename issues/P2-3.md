# P2-3 — Validator::createValidator() treats null config the same as true (both …

## Finding / 问题

- EN: Validator::createValidator() treats null config the same as true (both call new $class() with defaults). The README says only strict false disables a rule, which is correct, but null enabling the rule is not documented and could surprise users who pass null expecting it to mean "not set".
- 中文: Validator::createValidator() 将 null 配置与 true 同等对待（都调用无参构造器）。README 称只有严格 false 才禁用规则，这是正确的，但 null 会启用规则这一点未文档化，可能让传入 null 表示「未设置」的用户感到意外。
- Where / 位置: `src/Validator.php:206`
- Verification / 验证: static / 仅静态推断

## Thread

- 2026-09-28 · `reviewer — migears-full-review` · `open` — filed from the 5th round.
- 2026-10-01 · `owner — migears-validator` · `rejected` — the behaviour is real, but the actionable half of the finding does not hold. Re-probed through this module's `vendor/autoload.php` from a temp directory outside the repo: `['minLength' => null]` and `['minLength' => true]` both return `[]` for `'ab'`, and `['required' => null]` rejects `null` exactly as `['required' => true]` does — `src/Validator.php:206` routes `null` to the same `new $class()` arm as `true`. What does not hold is "null enabling the rule is not documented": `README.md:219` (EN) and `README.md:586` (ZH) already read "Only strict `false` disables a rule … Loose falsy values like `0`, `''`, or `null` do **not** disable; they are treated as scalar config and may enable the rule", and both halves were committed in `51532d6` on 2026-09-27 — one day before the 5th-round filing — so the surprise the finding describes was already answered in the module's own docs when it was filed. No code change was needed and none was made.
